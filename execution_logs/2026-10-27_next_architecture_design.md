### 公式資料で確認した制約
- KVは結果整合で、変更伝播は60秒以上かかる場合もあり、原子的なread/modify/writeには向かない。[Cloudflare KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/)
- SQLite-backed DOにはトランザクションAPIがある。外部KV I/Oまで同じトランザクションにはできない。[DO storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- DO Alarmは各DOに1個、少なくとも1回実行・失敗再試行の性質を持つ。期限ちょうどの物理削除保証として使わない。[Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- Web CryptoのwrapKeyは対象鍵がextractable=trueであることが必要。非抽出鍵を後からそのまま共有できる設計にはしない。[MDN wrapKey](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/wrapKey)

## 2. 推奨設計（未実装）

### 2.1 仕様の適用単位と期限
- 通常メモ、共有パッド、添付原画像、サムネイル、競合退避、送信待ちドラフト、Oracleの複製を対象にする。長期タスク/日次巡回も例外にしない。プリセット・認証・鍵・本文を含まない墓標はメモ本文ではなく、別の保持方針にする。
- 設定はワークスペース共通 `retentionSeconds ∈ {300,900,1800}`、初期値300。設定変更は将来の有効な内容編集から適用し、既存expiresAtは変えないことを推奨する。設定画面にも明示。現在のメモまで再計算する要望が出たら別仕様とし、閲覧で延長する仕組みにはしない。
- DOが実際に内容変更を受理した時刻を `contentUpdatedAt` とし、`expiresAt=contentUpdatedAt+retentionSeconds`。タイトル/本文/属性/画像追加削除などユーザーの意味的な編集だけが更新。読取、定期同期、同一内容保存、同じ操作の再送、鍵再ラップ、暗号文再配置では不変。
- サーバーは平文を見ないため、内容同一性の完全な検証はできない。信頼クライアントが正規化内容のHMAC（端末群の別用途鍵）をcontentTagとして送り、DOは同じタグのsaveをno-opにする。暗号文のランダムIV変更だけで延命させない。タグは同じレコード内の同一性を漏らす。悪意ある認証済みクライアントの虚偽タグは防げない。
- GET/list/blob/変更APIすべてでDOの時刻 `now >= expiresAt` を拒否条件にする。期限切れになった後の編集受付も拒否。Alarm未実行でもこの判定は有効。
- 画像は所有レコードと同じ寿命。本文を編集すると添付画像もそのレコードの期限まで有効。添付を外した場合はその画像参照を直ちに無効化。画像を別メモへ再利用するときは明示操作で新規暗号化し、期限切れ画像を自動的に複製しない。
- オフライン既存メモ編集は元expiresAtを超えて保存/再送しない。初回オフライン新規作成は暫定ローカル期限（5/15/30分）を持ち、期限内にだけ明示的新規作成として同期する。端末時計を信用できない/再起動後に検証できない場合は復号表示を保留。オフライン編集時刻の厳密証明はできないため、公式の最終更新はオンライン受理時刻と定義する。

### 2.2 Cloudflareの役割分担
| 層 | 役割・保持内容 | 禁止事項 |
|---|---|---|
| Worker | 認証、デバイス権限、入力サイズ/構造制限、DOへの転送、no-store応答 | KV単独の有効判定、平文復号、旧APIの代替書込 |
| ワークスペース単位DO（SQLite） | 単一の権威。レコード/期限/削除状態、単調sequence、採番、操作重複排除、設定、画像参照、失効通知、回収キュー | KV障害時に期限検査を省略する処理 |
| KV | 大きい画像等の不変暗号文blobのみ。キーはepoch/id/blobVersion、TTLは回収補助 | memos全件正本、墓標正本、公開blob URL、本文有効性の判定 |
| 端末/Oracle | 暗号文キャッシュ、端末鍵保管、表示直前の検証、局所検索/復号 | 無期限平文キャッシュ、平文Markdownミラー、期限切れfallback |

- 小さい本文暗号文とメタデータはDOに置き、本文更新/削除の権威を1回のトランザクションで確定する。画像はバイナリ暗号文として別送し、本文編集で画像全体を再送しない。
- 画像upload: 認証付き仮upload許可→不変キーへ暗号文put→DOでbase/期限/世代再検証→参照commit。KV書込後に削除が先行していたらcommitを拒否し孤立blobを回収。仮uploadに短い期限と容量上限を付ける。未commit画像は取得不可。
- 画像readもDO経由で所有者/現在参照/期限を確認して取得し、返却直前に再確認する。署名URLを期限内でも使い回せる方式は即時削除と相性が悪いため採用しない。KV未伝播はDO/端末の暗号文から再試行できる範囲に限り、古いblobへフォールバックしない。
- DOはSQLトランザクション内で状態比較・期限判定・更新・sequence・通知用outboxをcommit。KV呼出しをトランザクションに混ぜず、awaitをまたぐ箇所は世代を再検証。通知送信失敗でもcommit済み削除を戻さない。
- Alarmは最も早い期限/回収再試行を設定し、期限索引からバッチ処理して再設定。GETでも遅延失効を確定できる。回収ジョブは冪等、失敗は継続再試行＋本文なし監視。KV削除/TTLは論理拒否と独立。

### 2.3 APIと古いクライアントの再登録防止
- v2例: `GET /api/v2/state?cursor=...`、`POST /api/v2/records`、`PATCH/DELETE /api/v2/records/:id`、認証付きblob取得/仮upload。共有パッドも同じレコード機構を使い、UI上だけ単一padとして扱う。
- レコード: schemaVersion, workspaceEpoch, id, kind, revision, keyId, contentTag, ciphertext/iv, blobRefs, contentUpdatedAt, expiresAt, state。本文/タイトル/画像/用途属性は暗号化。平文メタデータはID・時刻・サイズ・操作種別等の最小限。AADにはschema/epoch/id/keyId/payloadVersionを結合し、変更可能なexpiresAtを不用意に含めて再暗号化を要求しない。
- 操作: deviceId, epoch, operationId, baseRevision, intent, contentTag, encryptedPayload。サーバー採番revisionとsequenceのみ信用する。再送は同じoperationId、別payload再利用は拒否。重複応答に本文を保存しない。削除後の同操作再送は旧成功本文を返さず現在の終端状態を返す。
- 状態遷移: `ABSENT → LIVE → DELETED/EXPIRED`。終端からLIVEへ戻せない。updateは存在するLIVEだけ、upsert禁止。deleteは冪等で、最新状態を終端へ遷移させる（base競合で削除を無期限に失敗させない）。deleteより先にcommitした編集も削除され、後からの編集は410。
- createのIDはサーバーが単調採番し再利用しない。クライアントの旧id指定createを受け付けない。新規intent/operationIdは永続的に消費済みを記録（本文なし）。同一create再送で新IDを発行しない。大量化時はdevice操作連番の上限/消費範囲圧縮を設計し、単純な短期TTLで記録を消さない。
- 墓標は本文なしで保持し、差分イベントには保持期限を設けても、ID採番高水位・workspaceEpoch・操作消費情報は維持。古いcursorはresetRequiredにして権威snapshotでローカル置換。墓標回収後もunknown update/create旧idは拒否できる。
- v1全件POST、uninitialized seed、Markdown自動取込をサーバー側で停止。旧APIは426/410等で更新要求を返し、v2→v1互換平文配信もしない。旧SWの更新勧告だけには頼らない。epoch切替で旧ブラウザ/MCP/proposerのキューを拒否する。
- 新IDを発行して本文を手動コピーする認証ユーザーや、改変クライアントまで同一内容再登録を禁止することはE2EE下で保証できない。保証対象は旧id/旧世代/旧operationの再送と既知自動復元経路。正規クライアントには削除内容から新規作成するfallbackを設けない。

### 2.4 即時削除と端末表示
- delete commitの時点以降にDOで判定する新規読取/復号許可/更新を拒否する。削除した端末は即時消去、他の接続中端末へ削除sequenceをpush。ポーリング15/25秒を通信断検知・再接続補助として残す。
- pending deleteはローカル即時非表示＋暗号文キュー化し「全端末反映待ち」。オンラインcommit前に全端末削除済みとは表示しない。
- DOM、編集中本文、競合remote/backup、画像URL/ライトボックス、検索索引、未送信キュー、非同期画像変換・復号・fetch結果までepoch/revisionで無効化。失効はdirty/IME/フォーカスより優先。復帰時は表示前に期限/権威を照合し、時計不明や確認不能なら既存本文を隠す。
- 厳密な遠隔削除と、通信断中の既存本文の自由なオフライン閲覧は両立しない。推奨は既存本文の新規表示/Oracle復号をオンライン検証必須とし、通信断を検知した表示は閉じる。ローカル新規入力/暗号化保存は維持する。これは現行のオフライン閲覧からの仕様上の制約であり、未決事項として明示する。
- 通信断未検知中や既に送信済みの応答/表示まで「世界中で0秒」の保証は不可能。短い表示leaseでも遅延上限を縮めるだけ。期限自体は端末タイマー＋復帰時ゲートで保護するが、ブラウザ停止中の物理消去時刻は保証しない。

### 2.5 暗号鍵の共有・保管
- 信頼端末はスマホ/PC/iPadとOracleの限定復号サービス。Cloudflare、MCP利用AIは鍵の受領者にしない。認証トークンと暗号鍵を分離する。
- レコード/画像ごとにランダム256bit DEK、AES-256-GCM、毎暗号化96bitランダムIV・128bit tag。大量更新時の鍵/IV利用量にも上限。本文/画像のDEKはワークスペースのバージョン付きKEKでラップ。用途別鍵を分離しAADで取り違え防止。KVには暗号文、DOには暗号文/ラップ済み鍵のみ。
- 初回の信頼ブラウザがワークスペースKEKと回復用ランダム秘密を生成。永続データは端末保護鍵で暗号化したKEK。保護鍵は非抽出CryptoKeyとしてIndexedDBに保存し、平文鍵はlocalStorage/URL/ログへ保存しない。暗号化KEKを復号した瞬間の生バイトがメモリに存在することは認める。非抽出KEKを後からwrap/exportする矛盾を避ける。
- ペアリング: 新端末がP-256 ECDH公開鍵と短期チャレンジを登録→既存端末でQR/短い認証文字列を照合して承認→ECDH+HKDFの一時鍵でKEKを包み新端末へ送付。epoch/deviceId/チャレンジをAADへ結合、短期有効・一度のみ・レート制限。QRは公開鍵/チャレンジを基本とし、永続共通鍵入りURLは採用しない。公開鍵差替え対策として別画面で照合する。
- 回復用秘密は利用者がアプリ外の安全な保管先へ保存し、その鍵で包んだKEKのみサーバーへ置く。回復後は端末登録をやり直す。全端末と回復秘密を失えば復号不能。一般パスワードをそのまま暗号鍵にはしない。
- 失効端末は認証device権限を遮断し、KEK/keyIdを更新して残存LIVEデータのDEKを信頼端末で再ラップ。期限は延長しない。漏洩済み旧鍵/暗号文や端末保有のDEKを遠隔で無効化できるとは説明しない。
- XSSでは非抽出鍵でも復号操作や平文を盗める。CSP、外部script削減、Markdownの安全な描画、端末ロックが必要。物理鍵削除でストレージ/プロバイダバックアップまで消えるとは保証しない。

### 2.6 Oracle/MCP：残留と再登録経路を断つ
- 専用OSユーザーの `memo-crypto-broker` をOracle内の信頼復号端末にする。鍵はAIが使うシェル/MCPプロセスから読めない資格情報領域に保存し、起動時だけサービスへ渡す。環境変数、CLI引数、Git、チャット、一般workspaceへ置かない。通常SSHユーザーやAIにsudo/rootがあるなら分離は成立しないため、権限整理または別VMが前提。
- brokerはUnix socketのpeer資格情報とtoolスコープを検査。key export、任意ファイル読取、汎用decrypt toolは公開しない。MCPは期限検証済みのlist/get/update/create/deleteをbrokerへ委譲する。鍵なしMCPに平文キャッシュを書かせない。
- Oracleの復号前に必ずDOへレコードの現revision/期限/削除をオンライン照合する。接続不能/認証失敗/未知形式は取得不能を返し、ローカル/MEMOS.mdを読まない。期限/削除は処理開始だけでなくAI tool結果返却直前、長い巡回の各段階でも再検査。推論中に期限切れになった成果の自動再登録を拒否する。
- diskキャッシュを残すなら暗号文とid/epoch/revision/expiresAtだけ。プロセス再起動後も最初にDO照合。状態スナップショットに本文や復号DEKを保存しない。broker内平文は短時間メモリのみ、例外/監視に本文・画像を出さない。swap/core dump/temp/log/バックアップ経路も監査する。
- `memos_local_cache.json` と `MEMOS.md` の既存平文は削除許可後の移行対象として台帳化。新系からはどちらも参照/出力禁止。隔離や拡張子変更だけでは残留解消にならない。通常ファイルに期限付きメタデータを書くだけでもread側が無視できるので不可。
- Markdownは原則、本文なしの非機密ステータス/参照IDの索引に限定し、内容はMCPで取得する。Markdown風表示が必要ならbrokerが期限検証後にメモリ上でレンダリングし、永続ファイルにしない。平文Markdownエクスポートを残すなら、そのコピーは自動消去保証外になるため標準機能にはしない。
- 既存server.pyのcache-first、proposerのfallbackと全件POST、MCPのMarkdown parse/syncと失敗成功扱いをすべて廃止する。各巡回にはsource id/revision/expiresAtを渡し、内容の再登録は自動化しない。5分失効後の日次巡回は対象なしとして正常終了し、過去タスクを復元しない。
- AIには必要な平文だけをtool結果として渡し、鍵は渡さない。ただしAIに渡した平文、会話履歴、生成物、スクリーンショット等の回収は保証できない。AI側の保存を禁止する運用だけで完全消去と扱わない。厳密に残留を避ける用途は外部AIへ本文を送らない必要がある。

### 2.7 操作性・同期速度
- ローカル入力は即応、現行400ms/1秒のデバウンス、IME配慮、画像8枚の操作フローを維持。暗号化/圧縮は非同期で行い、IndexedDBの暗号文保存と小さな操作差分を使う。期限/削除による強制閉鎖は例外として優先。
- 接続中の変更/削除はDOのWebSocket通知、切断復帰はcursor差分、cursor失効時は完全snapshot。通知の順序sequenceとレコードrevisionで遅着応答を捨てる。画像重複転送を避ける。
- ベースライン未測定のため速度維持を完了とはしない。PC/iPhone/iPad/Oracleで同一回線・同一ダミーデータを比較し、入力応答/保存受付/他端末表示のp50,p95、転送量、CPU・電池を測る。暫定受入目標: 入力中の暗号処理起因50ms超のメインスレッド停止なし、保存受付p95の追加遅延100ms以内、接続中他端末反映は現行p95以内。実測で妥当性を確定し、強整合性を落として合わせない。

## 3. 残るリスク・実装前の判断事項

1. 即時削除の保証はDO commit以後の新規アクセス拒否。オフライン表示済み端末/通信中応答/AI受領済み内容まで即時消去はできない。オンライン必須表示の制約をUXに反映する必要がある。
2. 全データ5分化は既存の長期タスク/巡回と両立しない。確定仕様を優先して例外を作らず、失効前提の巡回へ移行する。
3. OracleがAIと同一UID・sudo権限を共有していれば鍵非共有の境界は成立しない。現状の実稼働権限は未監査。鍵保管製品/OS資格情報の具体採用は環境確認後。
4. 旧キャッシュ、Markdown、Git履歴、静的配信、バックアップ、監視、AI履歴の残留は別の台帳/削除計画が必要。今回それらを削除・読取していない。プロバイダのPITR/バックアップも論理失効と物理完全消去を分けて扱う。
5. 暗号化サーバーは意味的な編集の真偽や、新IDに複写した旧本文を完全には判定できない。正常クライアント/自動経路の復活防止と、悪意ある鍵保有者への対策を混同しない。
